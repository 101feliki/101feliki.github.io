Security: testing that proves it was authorised, and defences for AI-driven attacks

Autonomous, AI-driven attack tools are arriving fast. I built two things in response: a defence map that breaks one such tool down capability by capability for banks, and AEGIS, its deliberate opposite, an assessment suite that cannot act outside what a client signed off.

AEGIS: Authorized Engagement & Guarded Inspection Suite

An authorization-first assessment harness. Nothing runs unless the target is inside a signed scope and within the authorised time window, and every action, including every refusal, is written to a tamper-evident audit log.

  • Read-only by default: it checks reachability, configuration and exposure, never attacks application logic.
  • Transparent: requests carry an honest User-Agent naming the engagement, so the client's own team sees the authorised test in their logs.
  • Zero dependencies: pure Python standard library; ships as a single file or a checksummed Linux release with a locked-down service account, and the build is reproducible.
  • Two front doors: a local operator console ("type a website") and a command line.

Built for legal review

  • The scope file is HMAC-signed: a tampered scope fails verification and the run stops.
  • Each audit entry hashes the previous one, so changing any past entry breaks every later hash, and verify-audit re-checks the whole chain.
  • Every log records the SHA-256 of the build that produced it, proving which version created the evidence.
  • Checks on money-handling systems use only GET, HEAD and OPTIONS. Moving money or manipulating bets is deliberately not automated.

Ledger watchdog

Installed inside a client's environment, AEGIS checks whether the money adds up, read-only: it identifies the database, finds the bets, wallet and balance tables (a person reviews the map), and reconciles every bet against every wallet credit. Database passwords come from the environment and are never stored or logged; MySQL is read over TLS whenever offered.

ARTEX defence map

A structured breakdown of ARTEX, an open-source (AGPL-3.0), LLM-driven autonomous penetration-testing platform, written to build detection and defence services for Kenyan banks. Each of ten segments pairs the real source code with what it means for a defender:

  • Recon and discovery, web/API exploitation skills, mobile and binary reverse engineering, traffic interception.
  • The agent "brain" (planners, budgets, self-improvement) and local command execution with approval gates.
  • Data egress: captured traffic sent to LLM providers, a serious risk for any bank that runs such a tool.
  • The operator trust boundary: where the tool can turn on the people running it.
  • A final segment of defence signals: what a bank's monitoring should watch for.

How I approach security

Authorised, transparent, read-only first. I study attack tools to defend against them, and every assessment I build is designed so a client's lawyers and blue team can see exactly what was done, and that nothing was done outside what they approved.

The same thinking runs through my day job: the Mustek security dashboard, least-privilege database accounts, and audit logs on every staff action.
